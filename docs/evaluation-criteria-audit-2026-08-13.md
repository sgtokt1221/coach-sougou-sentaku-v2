# 添削・面接・提出書類 評価基準監査と改善案

- 監査日: 2026-08-13
- 対象: CoachFor総合型選抜 v2
- 対象範囲: 小論文添削、通常の模擬面接、提出書類AI添削、それらのスコア保存・表示・集計
- 対象外: ちょこ添削、各種ドリル、研究評価などの個別ミニ機能（ただし共通集計へ影響する箇所は確認した）
- 本文書の範囲: 調査結果と改善案。ランタイムコードの変更は含まない

## 1. 結論

小論文と提出書類は、2026-07-24の監査後にかなり改善されている。特に次は良い。

- 小論文と提出書類はAnthropicの構造化出力とZodを使用している。
- 小論文は合計点・字数・充足率をサーバー側で計算している。
- AP未取得時、小論文は40点満点、提出書類はAP評価を `null` にしている。
- 小論文は出題形式別、提出書類は書類種別ごとに一部基準を分岐している。
- 小論文の言語修正と提出書類の根拠引用は、本文に実在する文字列だけを残している。
- 小論文・提出書類にはプロンプト版とスキーマ版を保存する仕組みがある。

一方、現状の評価結果をそのまま生徒の成長比較や大学別の到達判定に使うのは危険である。特に面接は、採点定義・計算・画面表示が一致していない。

最優先で直すべき点は次の4つである。

1. 面接は画面上40点満点だが、動画ありでは最大50点を生成する。
2. プレゼン・口頭試問・集団討論の専用スコアをAIに生成させているが、保存前にすべて捨てている。
3. 面接終了APIは、採点対象の会話・モード・動画分析をクライアント入力に依存しており、評価の正本がサーバーにない。
4. 提出書類のAI添削結果が保存されず、再読込すると消え、バージョン履歴や講師画面にも安定して残らない。

また、3領域共通で次の問題がある。

- 「アプリ内ルーブリック」と「大学公式の評価基準」の区別が不十分。
- AP原文をそのまま使い、対象年度・選抜方式・出典・評価項目へ構造化していない。
- 評価できない軸を0点扱いしたデータと、本当に0点のデータが混ざる。
- 異なる満点・モード・プロンプト版のスコアを、そのまま同じグラフや平均へ入れている。
- 小論文で「設問が何を要求したか」と「答案がどこまで答えたか」を独立判定していない。
- 小論文で、文章の整い方に比べて議論の成熟度を十分に評価していない。
- 答案中の固有名詞・統計・制度名などが実在するかを検証していない。
- AIスコアと人間評価の一致度を測る継続的な評価テストがない。

## 4. 最優先の修正

### P0-1. 面接の満点が40点と50点で不一致

**判定: 確認済み不具合**

根拠:

- `src/lib/interview/score-core.ts:125-139` は、明確さ・AP合致度・熱意・具体性に `bodyLanguage` を加えて合計するため最大50点になる。
- 動画がない場合も `bodyLanguage = 0` とし、0点を合計へ入れる。
- `src/app/student/interview/[id]/result/page.tsx:196-251` は常に40点満点で割合・ランク・表示を計算する。
- `src/app/student/interview/history/page.tsx:168-220` も常に40点満点で表示する。
- `src/app/api/admin/analytics/monthly-trends/route.ts:131` は面接合計を40で割る。
- `src/app/api/interview/end/route.ts:223` は40点以上を高評価として扱う。

影響:

- 動画ありの面接は40点を超え、リング・パーセンテージ・ランクが100%を超え得る。
- 同じ内容でも、カメラを使っただけで満点と合計点の意味が変わる。
- 動画なしの `bodyLanguage = 0` は「評価不能」ではなく「最低評価」に見える。
- 面接平均、成長推移、スキル集計が比較不能になる。

改善案:

短期は、内容評価と伝達評価を分離する。

```ts
type InterviewScoreResult = {
  content: {
    criteria: Record<string, CriterionResult>;
    rawTotal: number;
    maxScore: number;
    normalizedScore: number; // 0-100
  };
  delivery: {
    assessability: "assessable" | "not_recorded" | "low_confidence";
    criteria?: Record<string, CriterionResult>;
    rawTotal?: number;
    maxScore?: number;
  };
  rubricId: string;
  rubricVersion: string;
};
```

- 通常の内容評価は4軸40点として維持する。
- ボディランゲージは別カード・別スコアにし、内容評価へ加算しない。
- どうしても総合へ含めるなら、動画の有無に関係なく同じ重みへ正規化し、`maxScore` を保存する。
- 未収録は0ではなく `not_recorded` にする。

受け入れ条件:

- 動画の有無で内容スコアの満点が変わらない。
- すべての画面・集計が保存済み `maxScore` または `normalizedScore` を使う。
- 100%を超える表示が発生しない。

### P0-2. 面接モード別スコアを保存前に破棄

**判定: 確認済み不具合**

根拠:

- `src/lib/ai/prompts/interview.ts:316-347` は、プレゼン・口頭試問・集団討論の追加軸をAIへ要求する。
- `src/lib/interview/score-core.ts:127-139` は `clarity`、`apAlignment`、`enthusiasm`、`specificity`、`bodyLanguage` だけを新しいオブジェクトへ詰め、追加軸を捨てる。
- `InterviewScores` 型と結果画面は追加軸に対応しているが、通常の採点経路では値が保存されない。

影響:

- 集団討論で最重要の協調性・傾聴力が総合点へ反映されない。
- 口頭試問で専門知識が誤っていても、明確で熱意があれば高得点になり得る。
- プレゼンで資料と発表が矛盾しても、専用軸が結果に残らない。

改善案:

- モードごとに判別可能なZodスキーマを作る。
- 共通軸を必要最小限にし、モード固有軸へ重みを割り当てる。
- 合計点はモデルではなくサーバー側で計算する。
- モード間比較は生点ではなく0〜100の正規化値を使用する。

推奨例:

| モード   | 推奨評価軸                                           |
| -------- | ---------------------------------------------------- |
| 個人面接 | 質問への応答、論理性、具体性、志望・AP接続、自己理解 |
| 集団討論 | 論点提示、根拠、傾聴・参照、協働、議論前進への貢献   |
| プレゼン | 構成、根拠資料、説明の明確さ、資料整合、質疑対応     |
| 口頭試問 | 正確性、推論過程、応用、誤り修正、説明力             |

受け入れ条件:

- 各モードの専用軸がAPI応答、Firestore、履歴、講師画面に残る。
- 専用軸が総合点へ実際に反映される。
- 同一モード・同一ルーブリック版だけで生点比較できる。

### P0-3. 面接の採点対象をクライアント入力に依存

**判定: 確認済み不具合／評価完全性の高リスク**

根拠:

- `src/app/api/interview/end/route.ts:21-43` はbodyの `userId` を先に信用し、ない場合だけトークンからUIDを取得する。
- 同ルートはセッション所有者の検証をせず、bodyの `messages`、`duration`、`mode`、`presentationContent`、`videoAnalysis` を採点へ渡す。
- セッションから `sessionMode` を読み出しているが、`scoreInterviewCore()` へ渡すのは `mode` である（`src/app/api/interview/end/route.ts:145-154`）。
- クライアントは終了時に会話と分析値をまとめて送っている（`src/app/student/interview/session/[id]/page.tsx:597-607`）。
- `GET /api/interview/[id]` は認証・所有者確認なしで結果を返す（`src/app/api/interview/[id]/route.ts:4-17`）。

影響:

- 会話の一部を削除・変更した内容で採点できる。
- 個人面接を集団討論等として採点させるなど、クライアント値で基準を変えられる。
- 動画分析値を変更し、ボディランゲージ点を操作できる。
- 評価データが本人の実施記録を表す保証がない。

改善案:

- `requireRole(request, ["student"])` を必須にし、bodyの `userId` は廃止する。
- セッションの `userId === auth.uid` を検証する。
- モード、大学・学部、提出資料はセッション保存値だけを正とする。
- 各ターンをサーバーへ逐次保存し、終了時は保存済み会話を採点する。
- クライアント分析を使う場合は生の集計材料と信頼度も保存し、範囲・時間・フレーム数をサーバー検証する。
- 結果取得APIにも本人または担当講師の認可を入れる。

### P0-4. 提出書類のAI添削結果を保存しない

**判定: 確認済み不具合**

根拠:

- `src/app/api/documents/[id]/review/route.ts:193-221` は `feedback` を組み立てて返すだけで、Firestoreへ書き込まない。
- `src/app/student/documents/[id]/page.tsx:230-248` は返却値をReact stateへ入れるだけである。
- 画面の再読込時は `versions[].feedback` から最新添削を探すが（同ファイル `132-138`）、現行reviewルートはそこへ保存しない。

影響:

- 再読込すると添削が消える。
- どの本文版に対する評価か追跡できない。
- 講師側の確認・改善前後比較・監査ログに使えない。
- プロンプト版を記録していても、評価自体が永続化されない。

改善案:

- 添削開始時に本文スナップショットまたは `contentHash` を確定する。
- AI評価成功後、同じトランザクションで評価レコードを保存する。
- 配列へ埋め込むより、`documents/{id}/reviews/{reviewId}` のサブコレクションを推奨する。

```ts
type DocumentReviewRecord = {
  id: string;
  documentId: string;
  versionId: string;
  contentHash: string;
  contentSnapshot: string;
  feedback: DocumentFeedback;
  rubricId: string;
  promptVersion: string;
  schemaVersion: string;
  model: string;
  createdAt: string;
};
```

- 現在本文と `contentHash` が違う場合は「この添削後に本文が変更されています」と表示する。
- 生徒画面と講師画面は同じreviewレコードを参照する。

## 5. 高優先度の改善

### P1-1. 面接だけ構造化出力・値検証・版管理がない

小論文・提出書類は `messages.parse()` とZodを使うが、面接は正規表現でJSONらしい部分を抜き、`JSON.parse()` した値をそのまま利用している（`src/lib/interview/score-core.ts:91-139`）。

不足している検証:

- 各スコアが数値・整数・0〜10であること
- 必須キーとモード別キーが揃っていること
- 引用が実際の会話に存在すること
- フィードバック件数と文字数の上限
- `stop_reason === "max_tokens"` の判定
- プロンプト版・スキーマ版・モデルの保存

改善案:

- `InterviewScoreOutputSchema` をモード別unionで定義する。
- Anthropic structured outputsを使用する。
- スコア合計はサーバー計算とする。
- 小論文・書類と同じ `aiMetadata` を `InterviewFeedback` に追加する。

### P1-2. 面接で前回データなしに前回比を要求

`src/lib/ai/prompts/interview.ts:369-382` は `improvementsSinceLast` を要求するが、`scoreInterviewCore()` は前回の会話・スコア・講評を渡さない。モデルが空配列にする保証もない。

改善案:

- 前回比較を今回の採点呼び出しから外す。
- 比較が必要なら、同一モード・同一ルーブリック版の前回結果を明示的に取得する。
- 前回と今回の根拠引用を両方持つ比較専用スキーマを使う。
- 比較対象がなければスキーマ上 `improvementsSinceLast: []` を確定する。

### P1-3. 異なる満点・モード・版を同じ平均とグラフに混在

根拠:

- 小論文はAPあり50点、APなし40点だが、`src/app/student/growth/page.tsx:203-231` と `src/app/student/dashboard/page.tsx:74-107` は生の合計点だけを使う。
- 成長画面の総合チャートは小論文と面接の生点を同じ0〜50軸へ描く（`src/components/growth/ScoresTrendChart.tsx:81-136`）。
- 管理者月次分析は小論文を一律50、面接を一律40で割る（`src/app/api/admin/analytics/monthly-trends/route.ts:106-132`）。
- 小論文画面は採点基準変更日を文章で注意するが、集計自体は版を分けない。

改善案:

すべての評価結果に次を必須保存する。

```ts
type ScoreIdentity = {
  rubricId: string;
  rubricVersion: string;
  rawTotal: number;
  maxScore: number;
  normalizedScore: number; // 0-100
  assessableCriteria: string[];
  mode?: string;
};
```

- 同一領域の時系列は、同一ルーブリック版を原則とする。
- 版をまたぐ場合は区切り線を入れ、必要なら旧スコアを新基準で再採点する。
- 小論文と面接の総合表示は、別線のままでも両方0〜100へ正規化する。
- 「最新スコア」は小論文と面接を混ぜず、領域別に表示する。

### P1-4. APを非構造化の長文として一律利用

現データを集計すると、大学JSONは12ファイル、学部は1,048件である。AP空欄は3件だが、2,000字超は110件、6,000字超は11件ある。一方、`prepareAdmissionPolicy()` は空白等を正規化した後、先頭6,000字で切るだけである。

`Faculty` 型にはAP本文はあるが、APの対象年度、選抜方式、項目別claim、出典、確認状態、公式配点がない（`src/lib/types/university.ts:59-79`）。長いAPには複数学科・一般選抜・教育方針等が混在する実データがある。

改善案:

```ts
type AdmissionPolicyClaim = {
  id: string;
  facultyId: string;
  selectionMethodId?: string;
  admissionYear: number;
  category:
    | "knowledge"
    | "thinking"
    | "initiative"
    | "collaboration"
    | "mission"
    | "other";
  text: string;
  sourceQuote: string;
  sourceUrl: string;
  retrievedAt: string;
  verificationStatus: "verified" | "needs_review";
};
```

- 書類・面接・小論文に関係するclaimだけを選んで渡す。
- 先頭文字数で切るのではなく、対象学科・方式の節を抽出する。
- APが存在しても、対象が特定できない場合は `insufficient_context` にする。
- 出典と対象年度を講師画面で確認できるようにする。

### P1-5. 内部基準を大学別の必要水準のように扱う

`src/app/api/admin/analytics/university-gap/route.ts:290-302` は、全大学で小論文36点、面接28点、各軸7点を必要水準として固定している。大学データ型には公式ルーブリックや合格最低点がないため、この値は大学別の公式基準ではない。

改善案:

- データ根拠がない値は `appTarget` と明示し、「必要点」「合格水準」と呼ばない。
- `requiredScores` は `appTargets` へ改名する。
- 大学公式値を表示する場合は、年度・方式・出典URL・対象科目を必須にする。
- 合否は書類、評定、資格、面接等の総合判定であり、AI単独スコアから推定しない。

### P1-6. 小論文でAPを全問題の固定20%にする

小論文はAPが取得できると、設問形式に関係なくAP合致度を5軸の1つとして等重みで合計する（`src/lib/essay/review-core.ts:148-161`）。また、設問の要求要素が欠けた場合に `logic` と `apAlignment` を4点以下にする指示がある（`src/lib/ai/prompts/essay.ts:82-89`）。

問題:

- データ分析問題や課題文読解で、APは直接の採点対象でないことが多い。
- 設問要求の欠落は主に「課題達成」と「論理」の問題で、APを必ず下げる理由にはならない。
- APを意識した単語や姿勢が、資料読解・設問応答と同じ10点を持つ。

改善案:

- 小論文の中核軸を `taskFulfillment`、`sourceComprehension`、`reasoning`、`organization`、`expression` にする。
- APは、大学公式に小論文の評価観点として確認できた場合、または設問がAP・志望と直接関係する場合だけ追加する。
- APは補助評価として別表示し、根拠がない限り総合点へ入れない。
- 現行データとの互換が必要なら、当面 `apAlignment` の重みを0にして参考値表示にする選択肢もある。

### P1-7. 提出書類の共通方針が書類種別基準と衝突

`src/lib/ai/prompts/document.ts:24-35` は活動報告書について「志望理由や将来像は求めない」と定義している。一方、同プロンプトへ常に挿入される `FACULTY_AGENCY_FOCUS_DOCUMENT` は、全書類で「本人が何を実現したいか」を最重視し、学部の学びと将来像の接続を求める（`src/lib/ai/prompts/shared.ts:31-35`）。

影響:

- 活動報告書が、活動の事実・役割・行動・成果ではなく将来像で評価される可能性がある。
- 研究計画書で、研究課題・先行研究・方法・実現可能性より志望物語が優先され得る。

改善案:

- `FACULTY_AGENCY_FOCUS_DOCUMENT` を志望理由書専用にする。
- 書類種別ごとに「必須要素」「加点要素」「評価対象外」を定義する。
- 共通軸は、指示充足・一貫性・具体的根拠・表現の4つ程度に限定する。

### P1-8. 面接の動画評価が未校正の固定閾値

`src/components/interview/VideoAnalyzer.tsx:578-586` は次の固定基準でボディランゲージ点を算出する。

- 笑顔30%以上で9点、10%以上で6点、それ未満は3点
- 姿勢安定度、うなずき回数にも固定閾値
- 重みは視線35%、笑顔20%、安定25%、うなずき20%

問題:

- 「笑顔が多いほど良い」は質問内容や面接形式に依存する。
- 神経多様性、障害、文化的な視線行動への配慮がない。
- 測定信頼度やフレーム不足を総合点へ反映しない。

改善案:

- 当面は点数ではなく「練習上の観察指標」として表示し、合計点へ含めない。
- カメラ品質、顔検出率、有効フレーム数、信頼度を保存する。
- 講師評価と突き合わせて閾値・重みを校正する。
- 笑顔は常時要求せず、表情の硬さや場面適合を補助助言に留める。
- ユーザーが非言語評価を無効化できるようにする。

type CriterionResult = {

### P1-10. 小論文で議論の成熟度を独立して評価しない

**判定: 設計上の高リスク**

現行の5軸は、構成・論理性・表現力・AP合致度・独自性である。次のように、内容が単純でも形式が整っていれば各6点程度を取りやすい。

- 序論・本論・結論があるため、構成6点
- 主張・理由・具体例があるため、論理性6点
- 文法的に読めるため、表現力6点
- APと本人経験を結びつけたため、AP合致度6点
- 本人経験が論の一部になっているため、独自性6点

この場合、議論が「みんなが意識すれば解決する」「政府が制度を作ればよい」のような単純な結論でも30/50点になる。反対意見に一文触れれば、形式上はさらに上の帯へ入り得る。

根拠:

- `src/lib/ai/prompts/essay.ts:33-77` の各軸は、文章構造、主張と根拠、表現、AP接続、本人固有性を詳しく見る一方、問題の複雑性、利害対立、実現可能性、副作用、前提の妥当性を独立して評価しない。
- `logic` の8〜9点は反論・別の立場への言及を求めるが、反論の強さやトレードオフの検討までは定義していない。
- `src/lib/ai/prompts/essay.ts:102-106` はフィードバックの優先順位を「書き方・表現 → 論の運び → 内容の深さ」とし、内容の深さを最後に置いている。
- 「知識不足そのものを責めない」という教育方針は妥当だが、知識量と推論の成熟度を分けていないため、単純化を減点しにくい。

改善案:

専門知識の多さではなく、次の「思考の成熟度」を評価する。

- 問題を一つの原因だけで説明していないか
- 利害関係者や異なる立場を正確に捉えているか
- 価値の衝突やトレードオフを扱っているか
- 解決策の実行主体・方法・費用・障害を検討しているか
- 副作用、例外、限界条件を考えているか
- 強い反対意見を踏まえて主張を修正できているか
- 具体例一つから社会全体へ飛躍していないか

推奨アンカー:

| 点数 | 議論の成熟度                                                 |
| ---: | ------------------------------------------------------------ |
| 2〜3 | 感想・スローガン中心。原因や仕組みの説明がない               |
| 4〜5 | 理由はあるが、単一原因・単一視点で問題を単純化している       |
|    6 | 原因と結果の仕組みを説明し、最低限の制約を考えている         |
|    7 | 複数の立場、利害、実行上の障害を扱っている                   |
|    8 | トレードオフ、副作用、強い反対意見を検討している             |
|    9 | 限界や反論を踏まえ、条件付きの主張へ更新している             |
|   10 | 問題設定そのものを問い直し、新しい見方を根拠付きで示している |

実装方法は2案ある。

1. `reasoningMaturity` を独立軸として追加し、APを補助評価へ移す。
2. 現行の `logic` を `basicReasoning` と `reasoningMaturity` に分ける。

単に軸を増やして満点を増やすのではなく、構成・表現などと重複しない定義にする。知識不足だけでは下げず、「与えられた材料からどこまで複雑さを考えたか」で評価する。

受け入れ条件:

- スローガン型、単一原因型、実行主体不明の解決策が高い成熟度点を取らない。
- 専門用語を多用しただけでは加点されない。
- 同じ文章構成でも、トレードオフや限界を検討した答案が明確に上になる。
- 指導経験者が「内容が幼い」と判定した固定答案で、旧版より適切に差が出る。

### P1-11. 虚偽・未確認の固有名詞や外部事実を検証しない

**判定: 確認済み機能不足**

現行対応は、次の2つに限られる。

1. AIへ「入力にない活動、成果、数値、固有名詞を追加しない」と指示している（`src/lib/ai/prompts/essay.ts:5-8`）。
2. 課題文・英文・グラフ等が与えられ、その資料と答案が食い違う場合は、`logic` を4点以下にするよう指示している（同ファイル `82-89`）。

しかし、これは「生徒が答案内に書いた外部事実が本当か」を確認する仕組みではない。

未実装の項目:

- 人物名、大学名、組織名、法律名、研究名、制度名、書籍名、統計値、年号、引用の抽出
- 与えられた資料・登録済み資料との自動照合
- 外部の公式・一次情報による存在確認
- `verified`、`contradicted`、`unverified` の区別
- 未確認情報をスコアの正の根拠に使わない制御
- AIが生成したブラッシュアップ文と原文の固有名詞差分検査

`src/app/api/essay/[id]/brushup/route.ts:95-135` は、生成後に見出し、文体、文字数を検査するが、新しい固有名詞・数値・事実が増えていないかは検査しない。したがって、プロンプトの禁止指示にモデルが違反しても保存される。

現状で想定される挙動:

- 「国立青葉大学の田中教授が提唱した青葉理論」のような架空名でも、モデルが偽物と気づかなければ通常の具体例として扱う。
- 固有名詞や数値があることで、現行 `logic` の「答案固有の事実・経験・数値」や `originality` の具体性として、むしろ加点される可能性がある。
- 有名な事実との矛盾をモデルの事前知識で偶然指摘することはあるが、再現性も根拠表示も保証されない。
- 生徒本人の活動名・地域団体名・校内制度など、外部検索で見つからない正しい事実もあるため、「検索結果なし＝嘘」とは判定できない。

改善案:

まず、断定的な「嘘判定」ではなく、claim単位の確認状態を持つ。

```ts
type ClaimCheck = {
  claim: string;
  type:
    | "person"
    | "organization"
    | "law_or_policy"
    | "research_or_book"
    | "statistic"
    | "date"
    | "quotation"
    | "personal_fact";
  status: "verified" | "contradicted" | "unverified" | "not_checkable";
  evidence?: Array<{
    title: string;
    url: string;
    sourceType: "official" | "primary" | "secondary";
    checkedAt: string;
  }>;
  impact: "central" | "supporting" | "incidental";
  note: string;
};
```

推奨フロー:

1. 答案から検証可能な固有名詞・数値・引用を構造化抽出する。
2. 課題文内の事実は、まず課題文との完全一致・意味的一致を確認する。
3. 公開事実は大学公式、官公庁、法令、論文などの一次情報を優先して照合する。
4. 本人の活動・校内制度等は自動で虚偽扱いせず、「本人・講師の確認が必要」にする。
5. 未確認claimは、確認が終わるまで高得点の根拠として使わない。
6. 中心的なclaimが公式情報と矛盾する場合は、`factualReliability` または `evidenceValidity` を下げる。
7. ブラッシュアップ後は、原文になかった固有名詞・数値・引用を差分抽出し、許可されていなければ保存前に再生成または削除する。

採点ルール案:

- `unverified`: 原則として即減点しない。ただし、根拠としての加点には使わず、確認警告を出す。
- `contradicted` かつ中心的: `evidenceValidity` を0〜3点、`logic` または `reasoning` を4点以下にする。
- `contradicted` だが周辺的: 総合点を大きく動かさず、事実修正を優先改善点にする。
- `personal_fact`: 自動真偽判定をせず、証明資料・担当講師・本人確認のステータスを付ける。
- 架空事例として明示した固有名詞: 虚偽扱いしない。事実例と架空例を区別する。

受け入れ条件:

- 原文にない固有名詞・数値をAIブラッシュアップが新規追加した場合に検知できる。
- 課題文と矛盾する固有名詞・統計を検知し、該当箇所を引用して警告する。
- 外部で確認できない個人的活動を、自動的に「嘘」と断定しない。
- 未確認事実が具体性・独自性の加点根拠にならない。
- 検証結果に参照した出典・確認日時・確認状態が残る。

### P1-12. 小論文で「設問に答えたか」を独立判定しない

**判定: 確認済み機能不足／設計上の高リスク**

現行プロンプトにも、設問が明示的に求める「比較」「方策」などが欠けた場合は重く減点する指示自体はある。しかし、これは独立した評価結果ではなく、`logic` と `apAlignment` を4点以下にする文章上の指示にとどまる。

そのため、次の答案を安定して区別できない。

- 同じテーマには触れているが、問われた主題とは別の話をしている答案
- 「比較せよ」に対し、一方だけを説明している答案
- 「要約したうえで意見を述べよ」に対し、要約だけ、または感想だけを書いた答案
- 「原因を分析せよ」に対し、解決策だけを述べた答案
- 「三つ挙げよ」に対し、一つしか答えていない答案
- 資料を踏まえる必要があるのに、資料と無関係な持論だけを述べた答案

根拠:

- `src/lib/ai/prompts/essay.ts:10-15` の採点軸に、設問適合性・課題達成度がない。
- 同ファイル `82-89` には重い減点指示があるが、要求事項ごとの充足判定、根拠引用、欠落理由を返す形式がない。
- 同ファイル `185-186` は「設問への直接的な応答」を重視すると書くだけで、点数アンカーも機械的な制限もない。
- `src/lib/ai/schemas/essay-review.ts:6-85` には `taskFulfillment`、`directAnswer`、要求事項別チェック結果がない。
- `src/lib/essay/review-core.ts:148-162` は既存5軸を合計するだけで、設問不適合時の総合点上限をサーバー側で適用しない。
- レポート課題は `focusPoints` を明示的な設問要件として持つ（`src/data/essay-report-materials.ts:96-100`）が、提出時は題名と課題文本文だけを送り、`focusPoints` を送っていない（`src/app/student/essay/new/page.tsx:934-939`）。
- 宿題経由は題名だけを `topic` として渡し、設問形式・資料・要求事項を渡していない（`src/app/api/student/homework/[id]/submit/route.ts:257-267`）。

現状で想定される挙動:

- 主題を外していても、文章が読みやすければ `structure` と `expression` は高く残る。
- 本人経験が具体的なら `originality`、APに接続していれば `apAlignment` も残り得る。
- 「設問不適合」が一つの明示的な判定として画面に出ず、利用者には単に論理点が低い答案に見える。
- 設問要件の渡し方が提出経路で異なるため、同じ答案でも通常提出、レポート、宿題で判定が変わり得る。

改善案:

まず、設問を単なる文字列ではなく、採点時点の構造化された `TaskSpec` として保存する。

```ts
type EssayTaskSpec = {
  promptText: string;
  requirements: Array<{
    id: string;
    operation:
      | "summarize"
      | "compare"
      | "analyze"
      | "evaluate"
      | "propose"
      | "argue"
      | "cite_source"
      | "give_examples";
    target: string;
    required: boolean;
    minimumCount?: number;
  }>;
  sourceUse: "required" | "optional" | "none";
  wordLimit?: number;
};
```

登録済みテーマ、過去問、レポート、宿題は、出題データの作成時に人が確認した `TaskSpec` を持たせる。自由入力の設問だけはAIで要件候補を抽出し、採点前に生徒または講師が確認できるようにする。採点モデル自身に毎回すべてを推測させない。

添削結果には、点数とは別に次を必須で返す。

```ts
type TaskFulfillmentResult = {
  overall: "direct" | "partial" | "off_target";
  requirements: Array<{
    requirementId: string;
    status: "met" | "partial" | "missing";
    answerEvidence: string[];
    reason: string;
  }>;
  interpretationNote?: string;
};
```

推奨アンカー:

|  点数 | 設問への応答                                                 |
| ----: | ------------------------------------------------------------ |
|  0〜2 | 主題が別、または設問が求める作業をほぼ行っていない           |
|  3〜4 | 関連する話題には触れるが、中心的な問いに答えていない         |
|  5〜6 | 中心的な問いには答えるが、必須要素・対象・個数の一部が欠ける |
|  7〜8 | すべての主要要件に直接答え、必要な資料も使っている           |
| 9〜10 | 全要件を統合し、答案全体が設問への回答として一貫している     |

採点制御:

- `off_target` は `taskFulfillment` を2点以下とし、正規化総合点の上限を暫定40%にする。
- 中心的な必須要件が欠ける場合は4点以下とし、正規化総合点の上限を暫定60%にする。
- 構成・表現は技能として個別表示してよいが、「文章は整っているが、設問には答えていない」と総合判定を先頭に表示する。
- 設問要件の欠落を理由に `apAlignment` まで自動で下げない。AP適合と設問適合は別々に評価する。
- 上限値は固定答案と指導経験者の採点で校正し、実データを見ずに合否水準として扱わない。
- 設問に複数の合理的解釈がある場合は `interpretationNote` を残し、講師が判定を変更できるようにする。

画面では、総合コメントより先に「設問への回答」チェックリストを出す。各要求事項について、答案中の該当箇所、未回答、部分回答を示し、次に何を一文追加・変更すべきかを案内する。

受け入れ条件:

- 同じテーマの別論点を整った文章で書いても、高い総合評価にならない。
- 「比較」「要約＋意見」「原因分析」「方策」「指定個数」の各要求を別々に検出できる。
- 各要求事項の判定に、答案中の該当箇所または「該当なし」が表示される。
- レポートの `focusPoints` と宿題の設問条件が、通常提出と同じ `TaskSpec` で保存・採点される。
- 合理的な別解釈を機械的に誤答と断定せず、講師が確認・上書きできる。
- 固定評価セットに、同一テーマだが主題を外した答案を含め、旧版より人手評価との一致が上がる。

## 6. 中優先度の改善

### P2-1. 自己分析・過去弱点を採点時に見せない

小論文・面接・提出書類は、自己分析や過去弱点を採点入力へ含める。個別助言には有用だが、純粋な採点では次のバイアスになる。

- 本文・回答に書かれていない強みを、書かれているように解釈する。
- 過去に「論理が弱い」と記録された生徒を、今回も弱いと判定しやすくなる。
- 自己分析の理想像と一致する回答を、内容以上に評価する。

改善案:

1. 第1段階: 提出物・会話・設問・確認済み資料だけでブラインド採点する。
2. 第2段階: 自己分析・過去弱点を使い、個別助言だけを生成する。
3. スコアと個別助言で使用したコンテキストを分けて記録する。

### P2-2. 宿題経由の小論文で出題条件が欠落

通常の小論文添削は `questionType`、`sourceText`、`chartDataSummary`、`lectureInfo`、`wordLimit` を渡せる。一方、汎用宿題の直接提出は題名・AP・弱点等だけを `reviewEssayCore()` へ渡す（`src/app/api/student/homework/[id]/submit/route.ts:257-267`）。`HomeworkAssignment.snapshot` にもこれらの条件がない。

改善案:

- 宿題snapshotに共通 `EvaluationTaskContext` を保存する。
- 通常提出、宿題、講座、再提出の全経路で同じ評価入力ビルダーを使う。
- 同一本文・同一条件を異なる経路から送っても、同じプロンプト入力になる統合テストを作る。

### P2-3. 改善文そのものを弱点IDとして蓄積

小論文・面接とも、`repeatedIssues[].area` に加えて `feedback.improvements` の自由文を弱点タグへ入れている（`src/app/api/essay/review/route.ts:341-368`、`src/app/api/interview/end/route.ts:175-220`）。その結果、表現が少し違うだけで別弱点になる。

改善案:

- 弱点は固定taxonomy IDだけを保存する。
- AIは `weaknessCategoryId` と根拠引用を返す。
- 自由文は弱点レコードの説明・今回事例として保存し、ドキュメントIDにしない。
- 同じtaxonomy内の重複はサーバー側でまとめる。

### P2-4. 提出書類が3軸のみで必須条件・正確性を独立評価しない

AP合致度・構成・独自性は重要だが、提出可否を判断するには足りない。例えば研究計画書は、独自性が高くても方法が実行不能なら問題である。

推奨基準:

| 書類種別     | 必須評価軸の例                                                             |
| ------------ | -------------------------------------------------------------------------- |
| 志望理由書   | 設問・指定要素の充足、経験と志望の因果、大学固有性、AP接続、具体性、表現   |
| 自己推薦書   | 強みの明確さ、根拠経験、本人の行動、成果の検証可能性、大学での再現性、表現 |
| 活動報告書   | 事実の明確さ、役割、行動、工夫、成果、学び。将来像は原則必須にしない       |
| 研究計画書   | 問い、背景・先行研究、方法、実現可能性、倫理・制約、期待成果               |
| 学びの設計書 | 学習目標、科目・研究環境との接続、履修順序、実現可能性、卒業後との接続     |

共通で最初に `taskFulfillment` を判定し、大学の設問・文字数・必須項目が不明なら「提出適合性は未評価」とする。

### P2-5. 人手評価付きの回帰テストを作る

現状は小論文に実答案を再採点して新旧差を見るスクリプトがあるが、正解となる講師評価や許容差を持たない。面接・提出書類には同等の校正経路がない。

最低限必要な評価セット:

- 小論文: 出題形式ごとに低・中・高品質、設問逸脱、資料誤読、APなしを含む。
- 面接: 4モード、短すぎる回答、長いが質問に答えない回答、APなし、動画なしを含む。
- 提出書類: 5種類、必須要素欠落、事実は具体的だが構成不良、APなしを含む。
- 各事例に指導経験者2名以上の軸別評価、重大誤りラベル、許容点差を付ける。

評価指標:

- 軸ごとの人手評価との平均絶対誤差
- 順位相関
- 同一入力を複数回採点したときの変動幅
- 評価者間一致度
- 引用根拠の正確率
- AP未取得時の誤断定件数
- モード・書類種別の取り違え件数
- 重大誤読・捏造・合否誤認は平均点とは別の失格条件にする

## 7. 推奨する共通評価モデル

3領域で別々の型を増やすより、共通の評価メタデータとcriterion形式を持たせる。

```ts
type EvaluationResult = {
  domain: "essay" | "interview" | "document";
  taskType: string;
  rubric: {
    id: string;
    version: string;
    source: "app" | "official";
    officialSourceUrl?: string;
    admissionYear?: number;
    selectionMethodId?: string;
  };
  criteria: Record<string, CriterionResult>;
  score: {
    rawTotal: number;
    maxScore: number;
    normalizedScore: number;
  };
  overallFeedback: string;
  priorityAction: string;
  metadata: {
    promptVersion: string;
    schemaVersion: string;
    model: string;
    createdAt: string;
    inputHash: string;
  };
};
```

重要な原則:

1. `0点` と `未評価` を分ける。
2. 合計はサーバーで計算する。
3. 比較には `maxScore` と `rubricVersion` を必須にする。
4. 内部目標と公式基準を名前・データ型・画面表示で分ける。
5. スコアは提出物だけで付け、自己分析・過去弱点は助言生成だけに使う。
6. 各軸に本文・会話の根拠引用を持たせる。
7. AI評価は合否判定ではなく、学習用の診断であると明示する。

## 8. 実装順序

### Phase 0: 数値の誤表示を止める

1. 面接のボディランゲージを40点の内容スコアから分離する。
2. 面接の全画面・集計で、保存済み満点を使用する。
3. APなし小論文を一律50点として集計する処理を直す。
4. 大学別分析の固定値を「アプリ内目標」と表示する。

### Phase 1: 評価結果を壊れない形にする

1. 面接を構造化出力＋Zodへ移行する。
2. 面接モード別スキーマとサーバー側合計計算を実装する。
3. 提出書類レビューを本文版と結びつけて永続化する。
4. 全領域に `rubricVersion`、`maxScore`、`normalizedScore` を保存する。
5. 面接終了APIをサーバー正本・所有者検証へ変更する。

### Phase 2: 基準の妥当性を上げる

1. 小論文でAPを補助軸へ変更し、課題達成・資料読解を中核にする。
2. 提出書類を種別別ルーブリックへ分け、共通方針の衝突を解消する。
3. CriterionResult形式で根拠引用・理由・次の行動を揃える。
4. 自己分析・過去弱点を採点呼び出しから分離する。
5. APを年度・方式・出典付きclaimへ構造化する。
6. 小論文へ `reasoningMaturity` を追加し、単純化・トレードオフ・実現可能性を評価する。
7. 固有名詞・数値・引用のclaim確認と、ブラッシュアップ前後の事実差分検査を実装する。
8. 全提出経路で `TaskSpec` を保存し、設問充足チェックと総合点ゲートを実装する。

### Phase 3: 校正と継続監視

1. 指導経験者が採点した固定評価セットを作る。
2. PRまたはプロンプト版更新時に回帰評価を実行する。
3. モデル・プロンプト版ごとの分布と変動幅を監視する。
4. 講師がAI評価を上書き・注記できるようにし、差分を次の校正データへ使う。

## 9. 受け入れ条件

改善完了の最低条件は次のとおり。

- 面接で40点を超えるのに `/40` と表示されるケースが0件。
- 動画なしをボディランゲージ0点として扱うケースが0件。
- 4つの面接モードすべてで専用軸が保存・表示される。
- 面接採点は認証済み本人のサーバー保存会話だけを使う。
- 提出書類の添削が本文版・プロンプト版とともに永続化される。
- APなし／対象不明は0点ではなく未評価になる。
- すべての総合点に `maxScore` と `rubricVersion` がある。
- 異なる満点のスコアを生点のまま同じ平均へ入れない。
- 固定の内部目標を「合格水準」「大学別必要点」と表示しない。
- 各高・低評価に本文または会話内の検証済み根拠がある。
- 幼いスローガン型答案が、構成・表現だけで高い思考評価を取らない。
- 未確認の固有名詞・数値を、具体性や独自性の加点根拠に使わない。
- AIブラッシュアップが原文にない固有名詞・数値を追加した場合に検知できる。
- 主題を外した答案が、構成・表現・AP合致だけで高い総合評価を取らない。
- 設問の各必須要件について、充足・部分充足・未充足と答案内の根拠が表示される。
- レポート・宿題を含む全経路で、同じ設問要件を保存して採点に使う。
- 同一入力3回の採点変動が事前に決めた許容範囲内に収まる。
- 人手評価付き固定セットで、旧版以上の一致度を保つ。
