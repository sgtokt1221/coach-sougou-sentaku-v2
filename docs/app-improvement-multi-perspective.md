# CoachFor総合型選抜（v2） 改善提案まとめ（多角的）

作成日: 2026-05-17  
対象リポジトリ: `coach-sougou-sentaku-v2`

このドキュメントは「設計書（`docs/design.md`）」や現行実装（`src/`）を踏まえて、**プロダクト/UX・AI品質・データ正確性・性能・運用・セキュリティ・開発体験**の観点から「次に何を変えると効くか」を整理したメモ。

---

## 0. 前提（このアプリの“勝ち筋”）

- 総合型選抜は「小論文・面接・書類・活動実績・自己分析」が**同時並行**で進むため、ユーザーに必要なのは「機能の数」より **迷わず前に進める“進行管理”**。
- AIは“答えを出す”より、**改善ループ（課題→練習→再評価→可視化）**を回すほど価値が出る。
- ドメインの勝負は「大学別AP/募集要項の正確さ」と「合格者データネットワーク効果」なので、**データ鮮度**と**信頼性（根拠の明示）**が最重要。

---

## 1. 強み（維持・伸ばすべき）

- 生徒/管理者/teacher/superadmin のロール分離とスコーピング方針が明確（`CLAUDE.md`）。
- 学習の主要要素（自己分析→小論文→面接→書類→活動→分析）を1つのプロダクトに統合できている。
- 面接は Realtime / 音声分析 / 視線・表情分析まで実装が進んでおり、差別化になりうる（`src/hooks/useRealtimeInterview.ts`、`src/app/student/interview/session/[id]/page.tsx`）。
- AI出力のJSON壊れに対して `jsonrepair` 等の現実的対処が入っている（例: `src/app/api/essay/review/route.ts`）。
- チュートリアル（`/tour/*`）で導線を作ろうとしている（`src/lib/tutorial/tour-routes.ts`）。

## 2. 最優先トップ10（効果が大きい順）

### P0（今すぐ）

1) **「次に何をすればいいか」を1画面で確定させる**
   - 例: 学習計画/締切/弱点/推奨アクションを統合し、ダッシュボードを“タスク指向”へ。
   - 成功指標: 初回登録〜24h内の「次アクション実行率」、週次継続率。

2) **大学データの鮮度と根拠表示をプロダクトに組み込む**
   - 例: AP/日程/方式の「最終更新日」「ソースURL」「年度」をUIに出す。誤り報告ボタンも。
   - 根拠: `docs/data-audit-pending.md` が示す通りデータは未確定部分が残る。

3) **TypeScript を“ビルドで落とす”運用へ戻す**
   - 現状: `next.config.ts` で `typescript.ignoreBuildErrors: true`。
   - 影響: 本番に型破綻が混入し、AI・決済・権限周りで事故りやすい。

4) **AI出力の“品質保証ライン”を作る（Zod + リトライ戦略の標準化）**
   - 現状: ルートごとにJSON抽出/修復がバラつきがち。
   - 例: `parseAiJson(schema, rawText)` の共通ユーティリティ化、失敗時は「再プロンプト→再生成」を統一。

5) **AI会話UXの“分割ルール”を厳格化（勝手に分割しない）**
   - 例: `splitIntoUtterances` は【】を見つけると機械的に分割するため、モデルが【注】等を出すと1セリフが分割される可能性。
   - 改善案: モード別に分割をON/OFF、もしくは行頭の既知prefixのみを分割対象にする。

### P1（次の1〜2週間）

6) **生徒の“改善ループ”をテンプレ化（弱点→ドリル→再計測）**
   - 例: 弱点ごとに短い練習メニュー（60〜180秒）を生成し、面接/小論文で再計測して改善判定。
   - 成功指標: 弱点の解消率（3回連続指摘なし）・提出/練習の頻度。

7) **管理者ポータルに「介入キュー」を作る**
   - アラートは揃ってきたので、次は「誰に」「何を」言うかのテンプレ＋記録（対応済み/保留/次回）を回せるUIへ。

8) **プライバシー設計を明文化（音声/映像/答案の保持と削除）**
   - 未成年/受験というセンシティブ領域なので、保持期間・用途・削除手段をUIと規約で一体化。

### P2（中期）

9) **パフォーマンスの“重いところだけ”分割・遅延ロード**
   - 例: `@mediapipe/tasks-vision`、PDF処理、グラフ周りを動的import/worker化し、初期表示を軽くする。

10) **観測（Observability）を整備して、AI/決済/権限の失敗を追えるようにする**
   - 例: ルートごとの失敗率、AIパース失敗率、Realtime接続成功率、Stripe webhook 重複率。

## 3. 領域別の改善案

### 3.1 UX / プロダクト設計（“迷い”を消す）

- **学習の全体像を「受験カレンダー + 完了率」で見せる**
  - 受験は期限が本質。志望校ごとに “今週やるべき” を出す（書類・面接・小論文・活動）。
- **「機能」から「状態」へナビゲーションを切り替える**
  - 例: サイドバーで「未完了」「期限近い」「伸び悩み」など状態別の入口。
- **AIの出力形式を“学生が実行できる粒度”に揃える**
  - 例: 改善点は「次に書く1文」「次に答える1フレーズ」まで落とす（抽象→具体の階段）。
- **エラー時のUX（復帰導線）を統一**
  - “再試行/保存済み/問い合わせ”を同じ位置・同じ表現にする。

### 3.2 学習設計（継続と成長実感）

- **週次レビュー（5分）をプロダクト内に標準搭載**
  - 今週の提出/練習数、伸びた点、次週の重点、講師への相談事項。
- **「弱点」ではなく「伸びしろ」を中心に言い換える**
  - 心理的負担を減らし、継続率を上げる。改善済みの演出は強く（称賛・可視化・ストリーク）。
- **練習の“間隔反復”**
  - 同じ弱点を2〜3日後に再テストする導線（通知/予定に組み込む）。

### 3.3 AI品質 / 体験（“賢い”より“安定”）

- **共通のAIガードレール**
  - 1ターン1質問、箇条書き禁止などの「UX制約」はプロンプトとUI両方で担保。
- **構造化出力の型検証を全ルートに適用**
  - Zodで `safeParse` → 失敗なら `jsonrepair` → それでもダメなら再生成、の統一。
- **AIコスト最適化**
  - 1) まず軽量モデルで下処理、2) 重い評価のみ高性能モデル、の段階化。
- **会話ログの再利用**
  - “前回の弱点”を次回の面接/添削に自動反映し、継続するほど精度が上がる体験に寄せる。

### 3.4 データ鮮度 / 正確性（信頼の土台）

- **年度（入試年度）を全データの第一級属性に**
  - AP/日程/方式は毎年変わる。UI上も「2027年度入試」などを明示。
- **更新フローのプロダクト化**
  - 収集→差分→レビュー→反映のパイプライン（スクレイパー計画は `docs/data-audit-pending.md` に沿って進める）。
- **根拠と免責をUIへ**
  - “参考情報”の扱いを統一し、誤情報のリスクを下げる。

### 3.5 パフォーマンス（最初の1秒を速く）

- **重い依存の遅延ロード**
  - Mediapipe / PDF解析 / グラフを画面単位で dynamic import。
- **クライアント状態の肥大化を抑える**
  - 大きい配列（ログ/レポート）を常時stateに持たず、ページング・仮想化・要約で扱う。
- **キャッシュ戦略**
  - 大学データや合格者統計など、頻繁に変わらないものはSWR + ETag/再検証で通信削減。

### 3.6 信頼性 / 運用（壊れない仕組み）

- **Stripe webhook の冪等性**
  - event.id を保存して二重処理を防止（Firestore transaction）。
- **AI処理のタイムアウト/リトライ標準**
  - `maxDuration` の統一、ユーザーへの“進行中”表示、失敗時の再実行。
- **Realtime接続失敗のフォールバックUX**
  - “次に試せる時刻”や“テキストモードへ切り替え”の導線を明確に。

### 3.7 セキュリティ / プライバシー（未成年×受験の前提）

- **データ分類（PII/センシティブ）の棚卸し**
  - 音声・映像・答案・評価・弱点は扱いを分ける（保存期間/閲覧権限/削除）。
- **権限（managedBy）の漏れ検査**
  - API/Firestore Rules の両面で“見えてはいけないデータ”が見えないことをテスト化。
- **ログのマスキング**
  - AI入力/答案全文をログに残さない方針（必要ならハッシュ/要約のみ）。

### 3.8 開発体験 / 品質（開発速度を落とさない）

- **TypeScriptのビルド通過を必須に**
  - `ignoreBuildErrors` を外し、CIで `npm run build` をゲートにする。
- **E2E（Playwright）の“最低限の守り”**
  - ログイン→提出→結果表示→管理者閲覧、の最短経路だけでも自動化。
- **AIルートの契約テスト**
  - 代表的なプロンプト入力に対し、JSONがZodを通ることをテストする（回帰を防ぐ）。

## 4. 実装の当たり所（例）

- 体験設計/データ鮮度: `docs/design.md`, `docs/data-audit-pending.md`, `src/data/*`

- ビルド品質: `next.config.ts`, `eslint.config.mjs`, CI（未整備なら追加）

## 5. 進め方（提案）

1) **North Star** を1つ決める（例: 「受験完走率」or「提出/練習の週次継続率」）
2) トップ10のP0を1〜2個だけ選び、2週間で出す（“全部やらない”）
3) 変更前後で指標を取って、効いた施策をテンプレ化して横展開

---

## 6. 付記（リスク）

- 大学データの不正確さは、UXやAIが良くても信頼を毀損するので最優先で扱うべき。
- 音声/映像は体験価値が大きい一方、プライバシーと運用コストが大きい。保持と削除の設計を先に固める。
