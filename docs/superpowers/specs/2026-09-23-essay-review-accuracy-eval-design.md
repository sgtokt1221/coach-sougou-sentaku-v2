# 小論文添削の精度検証：設計と実装計画

作成日: 2026-09-23
対象: `reviewEssayCore`（`src/lib/essay/review-core.ts`）と、その別呼び出し
`source-engagement-judge.ts` / `knowledge-judge.ts`
対象外: 面接の採点、出願書類の添削、ちょこ添削・各種ドリル（別の検証にする）

## 1. 結論

検証は必要で、いまは「添削の精度」を数字で言えない状態にある。

- プロンプトは v3→v24 まで実答案で校正してきたが、**不具合はすべて本番で生徒が受けてから見つかっている**
  （`src/lib/ai/prompt-versions.ts` の履歴。v5 全員同点、v13 同じ答案が 17点↔25点、v12 主題に答えている答案が 28→18点、v22 弱点の自己強化）。
- 2026-08-13 の監査（`docs/evaluation-criteria-audit-2026-08-13.md` P2-5）が「人手評価付きの回帰テストがない」と指摘したまま、未着手。
- 2026-09-23 に知識判定が「抗菌薬の過剰摂取は耐性菌の主因ではない」という誤った指摘を出した（山内さんの答案）。
  指摘の中身が正しいかを見る仕組みがない。
- 既存の `scripts/calibrate-essay-review.ts` は「旧版の点との差」を出すもので、正解との比較ではない。1回しか採点しないので揺れも見えない。

「精度」は1つの数字ではなく、次の3つに分けて測る。人手が要るのは (B) と (C) の一部だけなので、(A) と方向テストから先に始められる。

| 何を測るか                      | 意味                                                         | 人手 | 着手      |
| ------------------------------- | ------------------------------------------------------------ | ---- | --------- |
| (A) 再現性                      | 同じ答案を3回採点して、点がどれだけ揺れるか                  | 不要 | すぐ      |
| (A') 方向テスト                 | 答案に既知の欠陥を入れたとき、点が期待どおりの方向に動くか   | 不要 | すぐ      |
| (B) 妥当性                      | 講師の採点とどれだけ一致するか                               | 要   | 講師の時間 |
| (C) 指摘の正確さ                | 赤ペン・知識の誤り・引用が本文に実在し、内容が正しいか       | 一部 | すぐ／要  |

守る原則（`~/ObsidianVault/wiki/tech/llm-api.md` の学び）:
**一貫性は精度ではない。** (A) が良くても (B) が悪ければ「安定して間違えている」。精度の正解は人手でしか作れない。
別のモデルを審判に立てる案は、同族の好みが混ざるので正解の代わりにならない（参考値にとどめる）。

## 3. 指標

| 指標                     | 測り方                                                                                   | 仮の合格ライン                                   |
| ------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 再現性（合計）           | 同一答案 3回の合計点の範囲（max−min）                                                    | 範囲 ≤ 3点。ランク境界を跨ぐ答案が 1割以下         |
| 再現性（軸）             | 軸ごとの範囲                                                                             | 範囲 ≤ 2点                                       |
| 人手一致（軸・合計）     | 講師2名の平均との平均絶対誤差（MAE）                                                     | AI–講師の MAE ≤ 講師–講師の MAE                   |
| 順位一致                 | 講師平均との Spearman 順位相関                                                           | ≥ 0.7                                            |
| 評価者間一致             | 講師2名の MAE                                                                            | （AI の上限の目安。数値目標は置かない）           |
| 主題ずれの検出           | 意図的にずらした答案で `subjectMatch ≠ same` かつ内容4軸 ≤ 3                             | 検出率 100%（オラクル）                          |
| 正常答案の誤検出         | 主題に答えている答案で `subjectMatch = same`                                             | 誤検出 0                                          |
| 資料誤読の検出           | 課題文と矛盾する答案で `misreadings` 非空                                                 | 検出率 100%                                       |
| 方向テスト               | 結論削除／字数半減／主題差し替え版が、元より低い点になるか                                 | 全ペアで期待方向                                  |
| 指摘の実在率             | `languageCorrections[].original`・`knowledgeInsights.errors[].claim` が本文に実在する率   | 100%（プログラムで検査）                          |
| 指摘の正しさ             | 講師が指摘1件ごとに ○×                                                                   | 誤り率 ≤ 5%。知識判定の critical は誤り 0          |
| 途中終了・失敗           | `stop_reason = max_tokens`、パース失敗、別呼び出しの null                                | 0                                                |
| 費用・時間               | `usage` から算出、1件の所要秒数                                                          | 目安を持つだけ                                   |

合計点だけで見ない。分布が p10–p90 で 18〜31 の狭い帯なので、合計点の一致は簡単に見えてしまう。
軸ごとの一致と、両端（明らかに良い／悪い答案）の扱いで判断する。
ランクは `scoreToSkillRank()`（`src/lib/history-rank.ts`）の境界を使う。

### 見える差の大きさ（ノイズ床）

34件 × 3回で、合計点の平均の差は **1点** まで見える（1件の揺れの標準偏差を 2点と置くと、
平均の標準誤差は 2 / √34 ≈ 0.35点。3回の平均を使えばさらに小さい）。
Phase 3 で「直したら平均が 0.5点動いた」は揺れの範囲であり、判断に使わない。
**軸ごとの合格ラインの上下や、方向テストの合否のような、離散の変化で判断する。**
Phase 1 の実測で 1件の揺れがこれより大きければ、回数を増やすか、この節を書き直す。

## 4. 検証セット

**34件**。本番の実答案 24件 ＋ 作成答案 10件。

### 本番の実答案（24件、層化抽出）

| 層                                    | 件数 | 理由                                     |
| ------------------------------------- | ---- | ---------------------------------------- |
| 通常・低得点帯（≤ 22）                 | 5    | 密集の外側                               |
| 通常・中得点帯（23〜29）               | 6    | 本番の大半                               |
| 通常・高得点帯（≥ 30）                 | 4    | 上限の解像度                             |
| report（課題文型）                     | 4    | 資料読解の減点が効いているか（本番に5件） |
| やり直し（parentEssayId あり）のペア   | 2組（4件） | 「伸びた」判定が正しいか            |
| 提出者                                | 7人全員から最低1件 | 2人で 37件を占める偏りを薄める |

口頭試問型は本番に1件しかなく、その1件は設問が保存されていない（9/21 の不具合）。
実答案の層には入れず、作成答案 N9 で経路を確かめる。

答案本文には氏名等が含まれ得るので、**リポジトリに置くのは答案 ID だけ**。本文は実行時に Firestore から読む
（`calibrate-essay-review.ts` と同じ読み取り専用経路）。得点帯は保存済みの点で分けるが、
その点は v16〜v24 の混在なので、層分けの目安にだけ使う。

### 作成答案（10件、意図的な欠陥）

`src/data/essay-past-questions.ts` の過去問を1題選び、講師（または Claude）が
**基底答案を新しく書く**。そこから欠陥を1つずつ入れた版を作る。
実答案から派生させない（派生させると本文に個人情報が残り、repo に置けない）。
人手の正解が要らず、「ルーブリックが効いているか」を機械的に見られる。

| 番号 | 欠陥                                       | 期待                                        |
| ---- | ------------------------------------------ | ------------------------------------------- |
| N1   | 白紙（1文だけ）                            | 内容4軸 ≤ 2、失敗しない                     |
| N2   | 定型文の使い回し（設問語を含まない一般論） | `subjectMatch = different`                  |
| N3   | 主題の近い語への差し替え                   | `subjectMatch = different`                  |
| N4   | 結論の段落を削除                           | 構成が元より下がる                          |
| N5   | 課題文の主張と逆のことを筆者の主張として書く | `misreadings` 非空、logic ≤ 4               |
| N6   | 主述のねじれを3か所入れる                  | 赤ペンが3件、実在率 100%                    |
| N7   | 字数を制限の 6割に削る                     | 充足率の減点                                |
| N8   | 架空の統計・固有名詞を足す                 | `claimChecks` に unverified、加点されない   |
| N9   | 口頭試問型で正しい知識の記述（小問集合は `oral-exam/generate` で作り本文ごと保存） | knowledge の errors が空、満点 60 |
| N10  | 明らかに優秀な答案（講師が書く）           | 合計 ≥ 40                                   |

N1〜N8 は基底答案から作る。N9 は別の題（知識を問える分野）で作る。
作成答案は設問・資料・本文ごとリポジトリに置く（個人情報なし）。

### 人手の正解

- 講師2名が、AI と同じ軸基準で軸別 0〜10 を付ける。基準は `src/lib/ai/prompts/essay.ts` の
  各軸 3〜10点の記述を **1枚に抜粋したシート** にする（プロンプト全文は渡さない。長すぎて読まれない）。
- 講師には **設問・出題形式・字数制限・課題文（report なら全文）** を答案と一緒に渡す。
  設問を見ずに採点すると、回答力の軸が付けられない。
- AI の点は見せない（見せると引きずられる）。
- 1件あたり 10分 × 34件 ＝ 約6時間／人。これがこの検証で一番高いコスト。
- 指摘の正しさは、AI の赤ペン・知識の誤りを1件ずつ ○× で付ける（採点とは別のシート。こちらは AI の出力を見せる）。
- シートは Google スプレッドシート。列: 答案ID / 軸5つ / 合計 / メモ。
  CSV に落として `--human=` で読む。

## 5. 実装計画

### Phase 0: 計測の土台（半日、AI 呼び出しなし）

1. `reviewEssayCore` の戻り値に `usage`（3呼び出し分）、`stop_reason`、応答の `model`、所要ミリ秒を足す。
   保存経路（`/api/essay/review`）は `feedback.aiMetadata` に `usage` を残す（本番でも1件の費用が分かるようになる）。
   `aiMetadata` は `/api/essay/[id]` の許可リストに **入っていない**（2026-09-23 確認）。生徒画面で使う予定は無いので
   足さなくてよいが、管理者画面で費用を出すときは `/api/admin/students/[id]/essays/[essayId]` 側で読む
   （こちらは feedback を丸ごと返す）。
2. `scripts/eval-essay-review.ts` を作る。
   - 入力: `scripts/eval/essay-review-cases.json`（本番答案の ID と層のタグ、作成答案の設問・本文・期待値）
   - `--reps=3` `--ids=...` `--only=synthetic` `--human=<csv>` で対象と集計を切り替える。**読み取りのみ**。
   - 採点は **現行プロンプト（v24）** で行う。保存済みの点は使わない（版が混在しているため）。
     baseline ＝ v24 の採点結果。
   - 出力: `.claude/hillclimb/essay-review/baseline/results.jsonl` と `traces/<id>_rep<k>.json`
     （skill `claude-api` の評価レポート形式。1件終わるごとに書き、再実行は済んだ (case, rep) を飛ばす）
   - 失敗（API エラー、途中終了、パース失敗、別呼び出しの null）は `errors.jsonl` に分けて、0点として混ぜない。
   - 429／過負荷はジッター付きで退避して再試行し、回数を行に残す。同時実行は 3 まで。
   - 応答の `model` が `AI_MODEL_REVIEW` と違えばその試行を失敗にする（別モデルの点を混ぜない）。
   - 指摘の実在率と方向テストの判定はこのスクリプトの中で機械的に出す。
3. レポートは skill の `build-report-lite.mjs`（依存なし・15KB）を `scripts/eval/` に写して使う
   （skill の置き場はセッション限りで消えるため）。
4. `.gitignore` に `.claude/hillclimb/**/traces/` と `report.html` を足す。
5. 検証: 作成答案 N1 を1回だけ通し、行の `usage` / `stop_reason` / `model` / 所要秒が全部埋まることを確認してから先に進む。
   空の答案（N1）を通して内容4軸が低く出ること、作成答案 N10 が高く出ることも同時に見る（配線の確認）。

### Phase 1: 再現性・方向テスト・実在率（1日、AI 呼び出しあり）

1. 作成答案 3件で試走し、**実測の `usage` から費用を出して承認を取る**。
   上限の見積もり: 出力 16,000 tok × $15/M ＝ $0.24、入力 ~10,000 tok × $3/M ＝ $0.03 → 1回 ≤ $0.27。
   34件 × 3回 ＝ 102回 → **上限 $28**。実測は下回る見込み。
2. 全 34件 × 3回を回す。本番答案を読むので自動モードでは止まる。
   ユーザーが `! npx tsx --env-file=.env.local scripts/eval-essay-review.ts --reps=3` で実行する
   （9/23 の本番修正と同じ運用）。
3. 結果: 再現性の表、方向テストの合否、実在率、失敗件数。レポートは `scripts/eval/build-report-lite.mjs` で HTML にする。
4. ここで分かること: 揺れの大きさ、ルーブリックが効いていない箇所、指摘の捏造の有無。

### Phase 2: 人手一致（講師の時間 6時間／人）

1. スプレッドシートを用意し、講師2名に 34件を採点してもらう（AI の点は伏せる。設問・課題文を添える）。
2. `scripts/eval-essay-review.ts --human=<csv>` で MAE・順位相関・評価者間一致を出す。
3. 講師が「AI と違う」と感じた答案を3〜5件読み合わせ、どちらが妥当かを決める。**ここで初めてプロンプトの直し先が決まる。**

### Phase 3: 改善（結果を見てから決める。先に直さない）

候補。どれをやるかは Phase 1〜2 の数字で決める。

| 候補                                                     | 効きそうな症状                       | 注意                                                                     |
| -------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------ |
| 知識判定に「確信が無い指摘は挙げない」「教科書的に確立した誤りだけ」を課す | 指摘の誤り                           | 9/23 の件。critical/minor の基準も書き直す                                |
| 赤ペン・引用の実在検査をサーバー側で行い、無いものを落とす | 実在率 < 100%                        | 上限超過で全体を捨てない（llm-api.md の学び）                              |
| 温度を下げる                                             | 再現性が悪い                         | 揺れの原因が温度でなくルーブリックの曖昧さなら効かない。数字を見てから      |
| モデル／effort の見直し（`claude-sonnet-5` や `claude-opus-5` を低い effort で） | 人手一致が低い、費用             | 同じ eval で比較する。1件の費用も並べる                                    |
| 軸基準の書き直し                                         | 特定の軸だけ講師とずれる             | 版を上げ、eval を回してから出す                                            |

改善のたびに `v1/`, `v2/` として同じ eval を回し、baseline と並べる。**eval を回さずにプロンプト版を上げない。**

### Phase 4: 正解データを日常で溜める（別途判断）

講師が管理者画面の答案詳細で「この採点に同意する／自分ならこの点」を残せるようにする。
Phase 2 の5時間を一度きりにせず、次の検証セットが自然に育つ。
新機能なので、Phase 2 の結果を見てから作るか決める。

## 6. 決めること

| 論点                         | 推奨                                                           | 理由                                                    |
| ---------------------------- | -------------------------------------------------------------- | ------------------------------------------------------- |
| 人手採点を誰がやるか         | 講師2名                                                        | 1人だと評価者間一致が測れず、AI の上限が分からない       |
| Phase 1 の費用上限           | $28                                                            | 実測で承認し直す                                        |
| 作成答案の基底を誰が書くか   | 講師（N10 も兼ねる）。難しければ Claude が書き講師が目を通す   | Claude が書いた答案は AI 好みの文体になり得る            |
| 本番答案の扱い               | ID だけをリポジトリに置き、本文は実行時に読む                  | 個人情報を repo に残さない                              |
| Phase 4 の UI                | Phase 2 の後に決める                                           | 正解データの価値を確かめてから                          |

## 7. やらないこと

- 面接・出願書類の検証（別の eval にする。混ぜると一つも完成しない）
- eval の結果を見る前のプロンプト変更
- 別モデルを「正解」として使うこと（参考値まで）
- 本番データへの書き込み（eval は読み取りのみ）
