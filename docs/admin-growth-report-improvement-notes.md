# 管理者ポータル「成長レポート」改善メモ

## 目的

管理者ポータルには、生徒ごとの成長レポートを作成し、弱点・推奨アクション・類題を提示する機能がある。

現状でも「振り返りレポート」としては機能しているが、実際の個別指導・授業運用で使うには、類題や宿題の量、編集性、表示制御、授業への接続がまだ弱い。

このメモでは、成長レポートを **単なる振り返り資料** から **次回授業と宿題を組み立てる教材生成エンジン** に発展させるための改善点を整理する。

---

## 現状理解

### いまのレポートに含まれている主な要素

- 小論文の件数・平均スコア・前期間との差分
- 面接の件数・平均スコア・前期間との差分
- 弱点の進捗
- 推奨アクション
- 総合評価
- 講師コメント
- 類題
- 生徒への公開 / 非公開フラグ

### 類題の現状

現状の類題は、おおむね以下の設計になっている。

- `primary`: 授業中に扱う必須類題
- `secondary`: 宿題用の補助類題
- 生成数は固定で、基本的に `primary 3件 + secondary 2件 = 計5件`
- 小論文・面接の両方を含む
- 解答例 `modelAnswer` も生成される
- 管理者は編集モードで類題を追加・削除・編集できる
- 生徒画面でも同じ `ReportDetailCard` を read-only で表示している

---

## 大きな課題

## 1. 類題の量が授業・宿題運用には少ない

現在は計5件程度の想定だが、実際の授業で扱う教材としては少ない。

特に個別指導では、講師がその場で生徒の反応を見ながら問題を選びたい。  
そのため、最初から「ちょうど使う5問」だけではなく、「授業で使う候補」「宿題に回す候補」「予備問題」のような問題バンクが必要。

### 推奨する生成量

週次レポート:

- 授業用: 5問
- 宿題用: 8問
- 予備: 5問
- 合計: 18問程度

月次レポート:

- 授業用: 8問
- 宿題用: 15問
- 予備: 8問
- 合計: 30問程度

ただし、全問に長い解答例を付けるとAI出力もUIも重くなるため、問題の用途によって出力内容を変えるべき。

---

## 2. 類題の分類が粗い

現状は `primary` / `secondary` の2段階だが、授業運用では少し足りない。

### 推奨分類

```ts
usage: "lesson" | "homework" | "extra";
```

- `lesson`: 授業中に扱う
- `homework`: 生徒に課す宿題
- `extra`: 時間が余った時、または追加演習用

既存データとの互換性のため、当面は以下のように解釈する。

```ts
priority: "primary" -> usage: "lesson"
priority: "secondary" -> usage: "homework"
```

---

## 3. 解答例の見せ方にリスクがある

現状は、類題に `modelAnswer` が付く。  
授業用の解答例は講師にとって有用だが、生徒が宿題に取り組む前から解答例を見られると、宿題としての意味が弱くなる。

### 推奨する表示制御

```ts
answerVisibility: "teacher_only" | "after_submission" | "student_visible";
```

- `teacher_only`: 講師だけが見られる
- `after_submission`: 生徒が提出したあとに表示
- `student_visible`: 最初から生徒にも表示

初期値は以下がよい。

- 授業用: `teacher_only`
- 宿題用: `after_submission`
- 予備: `teacher_only`

---

## 4. 類題カードに授業用の情報が足りない

現状の `PracticeQuestion` は、主に以下の情報を持っている。

- type
- title
- priority
- relatedWeakness
- relatedPastTopic
- modelAnswer

しかし講師が授業で使うには、次の情報もあるとよい。

```ts
interface PracticeQuestion {
  id: string;
  type: "essay" | "interview";
  usage?: "lesson" | "homework" | "extra";
  priority?: "primary" | "secondary";
  title: string;
  relatedWeakness?: string;
  relatedPastTopic?: string;
  modelAnswer?: string;

  difficulty?: "basic" | "standard" | "advanced";
  estimatedMinutes?: number;
  objective?: string;
  rubric?: string[];
  hints?: string[];
  teacherNotes?: string;
  answerVisibility?: "teacher_only" | "after_submission" | "student_visible";
  order?: number;
  dueDate?: string;
}
```

特に重要なのは以下。

- `estimatedMinutes`: 授業内で時間配分しやすくする
- `difficulty`: 生徒の状況に応じて選びやすくする
- `objective`: 何を鍛える問題なのか明確にする
- `rubric`: 添削・講評の観点を揃える
- `hints`: 生徒に与える足場かけ
- `teacherNotes`: 講師向けの問いかけ・注意点

---

## 5. UIが「レポート表示」寄りで、「教材管理」にはなっていない

現状のUIは、類題カードを並べて表示する形。  
類題が5問程度なら問題ないが、15〜30問に増えると見通しが悪くなる。

### 推奨UI

類題欄を「問題バンク」UIにする。

必要な要素:

- `授業中` / `宿題` / `予備` のタブ
- 小論文 / 面接のフィルタ
- 難易度バッジ
- 目安時間
- 件数サマリ
  - 例: `授業 5 / 宿題 8 / 予備 5`
- 編集モード
  - 用途変更
  - 難易度変更
  - 解答例公開範囲変更
  - 問題追加
  - 問題削除
  - 並び替え
- 印刷時の宿題シート表示

初期実装ではドラッグ&ドロップまで不要。  
`order` と上下ボタンで十分。

---

## 6. 成長レポートとレッスン台本の接続が弱い

このプロジェクトには、すでにセッション画面に「レッスン台本」機能がある。  
一方で、成長レポートの類題はレポート内に閉じている。

理想的には、成長レポートで生成された授業用類題が、次回セッションのレッスン台本に接続されるべき。

### 望ましい流れ

1. 成長レポートを生成
2. 弱点に基づいて問題バンクを生成
3. 講師が次回授業で扱う問題を選ぶ
4. 選んだ問題が次回セッションの `prepPlan` に反映される
5. 授業後の `debrief` で、扱った問題と反応を記録
6. 次回レポート生成時にその結果を反映

この循環ができると、レポートが「出して終わり」ではなく、授業計画と学習履歴の中核になる。

## 優先度の高い改善

## P0: 先に直したい不具合・設計ズレ

### 1. レポート一覧の展開で新規生成している

管理者レポート一覧で詳細を展開する際、既存レポートを取得するのではなく、`/api/admin/reports/generate` をPOSTしている。  
これにより、単に詳細を見たいだけなのに新しいレポートが作成される可能性がある。

修正方針:

- 展開時は `/api/admin/reports/[studentId]/[reportId]` をGETする
- 新規生成は明示的な生成ボタンからだけ行う

### 2. 類題生成の期間判定に使う日付フィールドが揃っていない

通常レポート生成では、小論文は `submittedAt`、面接は `startedAt` を使っている。  
一方で、類題再生成では `createdAt` を使っている箇所がある。

これにより、同じレポート期間なのに、類題再生成時だけ今週の文脈が空になる可能性がある。

修正方針:

- 小論文は `submittedAt` を優先、なければ `createdAt`
- 面接は `startedAt` を優先、なければ `createdAt`
- 通常生成と再生成で同じ抽出ロジックを使う

### 3. 一括生成では類題が生成されない

一括生成では `practiceQuestions` が作られていない。  
大量生成時にAIコストが重くなるため、この設計自体は理解できるが、UI上で「類題は個別生成」と分かるようにした方がよい。

修正方針:

- 一括生成ではレポート本文のみ生成
- 詳細画面で「類題を生成」ボタンを明確に出す
- 将来的に `withPracticeQuestions: boolean` を追加してもよい

## 推奨実装フェーズ

## Phase 1: 安全な基盤修正

目的: 既存挙動を壊さず、明らかな不具合を直す。

実装内容:

- レポート一覧の展開APIをGETに変更
- 日付抽出ロジックを通常生成・再生成で共通化
- 一括生成後のUIで「類題未生成」を明示
- 既存 `priority` データを壊さない互換変換関数を作る

---

## Phase 2: PracticeQuestion 型の拡張

目的: 授業・宿題運用に耐えるデータモデルにする。

追加フィールド:

- `usage`
- `difficulty`
- `estimatedMinutes`
- `objective`
- `rubric`
- `hints`
- `teacherNotes`
- `answerVisibility`
- `order`
- `dueDate`

互換性:

- 既存の `priority` は残す
- 表示時に `priority` から `usage` を推定する
- 保存時は新フィールドを優先する

---

## Phase 3: 類題生成プロンプトを数量指定対応にする

目的: 固定5問ではなく、週次・月次・重め宿題などのプリセットに対応する。

例:

```ts
type PracticeGenerationPreset = "standard_weekly" | "heavy_weekly" | "monthly";
```

初期プリセット:

```ts
standard_weekly:
  lesson: 5
  homework: 8
  extra: 5

monthly:
  lesson: 8
  homework: 15
  extra: 8
```

出力方針:

- 授業用は解答例・講師メモまで出す
- 宿題用はヒント・採点観点中心
- 予備は問題文・狙い・難易度中心
- 全問に長文の解答例は付けない

---

## Phase 4: 管理者UIを問題バンク化

目的: 講師が授業前に問題を選び、編集し、配布できる状態にする。

実装内容:

- 類題セクションをタブUIに変更
  - 授業中
  - 宿題
  - 予備
- 件数表示
- 種別フィルタ
- 難易度表示
- 目安時間表示
- 編集モードの改善
- 解答例公開範囲の編集
- 印刷表示の最適化

この段階では、まだ宿題提出管理までは入れない。  
「レポートに付属する宿題シート」として成立させる。

---

## Phase 5: 生徒画面の表示制御

目的: 宿題として成立するよう、生徒に見せる情報を制御する。

表示ルール:

- `teacher_only`: 生徒には解答例・講師メモを表示しない
- `after_submission`: MVPでは非表示、将来的に提出後表示
- `student_visible`: 生徒にも表示

生徒画面で見せたいもの:

- 宿題一覧
- 問題文
- 目安時間
- ヒント
- 提出期限
- 関連弱点

生徒画面で隠したいもの:

- 講師用メモ
- 授業用の解答例
- 宿題の解答例

---

## Phase 6: 宿題配布・提出管理

目的: レポートの類題を実際の課題管理に接続する。

このフェーズはやや大きいので、後回しでもよい。

追加候補:

- `homeworkAssignments` コレクション
- 生徒の宿題一覧ページ
- 提出ステータス
- 提出本文
- AI一次添削
- 講師確認
- 提出後の解答例表示

想定API:

- `POST /api/admin/reports/[studentId]/[reportId]/assign-homework`
- `GET /api/student/homework`
- `PATCH /api/student/homework/[assignmentId]`
- `POST /api/student/homework/[assignmentId]/submit`

## Claudeに検討してほしい論点

1. 類題はレポート内の配列として持ち続けるべきか、それとも `practiceQuestionSets` のような別コレクションに切るべきか。

2. 宿題提出管理まで見据えるなら、最初から `homeworkAssignments` に分離した方がよいか。

3. 解答例はどこまで生成すべきか。全問生成すると重いが、講師の準備時間は減る。

4. 授業用問題とレッスン台本をどう接続するのが自然か。

5. 生徒向けには「成長レポート」と「宿題」を同じ画面に置くべきか、別画面に分けるべきか。

6. 週次・月次で生成する問題量はどの程度が妥当か。

7. 小論文と面接の比率は、生徒の志望校・直近弱点・出願時期によって動的に変えるべきか。

---

## 個人的な結論

最も効果が大きいのは、成長レポートを「親や生徒に見せる成果物」としてだけでなく、**次回授業の教材セット** として再設計すること。

そのためには、単に類題の数を増やすだけでは足りない。

必要なのは以下の3つ。

1. **量**: 授業・宿題・予備を含む十分な問題数
2. **運用**: 講師が選べる、編集できる、配布できるUI
3. **制御**: 解答例や講師メモを生徒に見せすぎない表示ルール

最初のMVPとしては、

- 類題を18問程度に増やす
- `usage` / `difficulty` / `answerVisibility` を追加する
- 管理者UIをタブ式の問題バンクにする
- 生徒には宿題用だけ見せ、解答例は隠す

ここまででかなり実授業に近づく。

その後、宿題提出管理やレッスン台本連携を入れると、Coach v2の有人個別指導向けの価値がかなり強くなる。
